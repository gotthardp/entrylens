# Instructions

Entrylens is a single door-mounted people-counting sensor: a VL53L8CX time-of-flight sensor
feeding a RAK3172 (STM32WLE5) MCU, which detects people and reports counts over LoRaWAN
(EU868).

## Files

Different files are authoritative for different things - flag it rather than assume if two
disagree.

- `DESIGN.md`: source of truth for design intent - power rails, current budget, operating
  states, and the debug/flashing scheme. Written and maintained by hand; read first.
- `datasheets/` and `components/`: source of truth for component characteristics (pin
  functions, electrical limits).
  - `datasheets/`: raw vendor datasheets and app notes. Read the local file first; only
    fetch from the web if no local copy exists.
  - `components/`: human-reviewed per-part extracts (`components/<PART>.md`, see
    `components/_template.md`) naming which datasheet(s) cover each part. Hand-curated, not
    auto-regenerated - re-check after a part swap. For parts without one, match the filename
    against the BOM's `Manufacturer Part` column directly.
- Export of the schematics and PCB: source of truth for the component list, designators,
  and exact part numbers. Auto-generated by the EDA tool; always use one same-dated set
  together, never mix revisions. Assume DRC was run by the designer before export - no
  report is generated.
  - `Netlist_Schematic1_*.net`: Protel2-format netlist.
  - `BOM_Board1_PCB1_*.csv`: bill of materials.
  - `Gerber_PCB1_*.zip`: fabrication Gerbers and drill files, plus `FlyingProbeTesting.json`,
    a per-pin net list extracted from the layout - usable to cross-check layout connectivity
    against the netlist.
  - `PickAndPlace_PCB1_*.csv`: component placement (position, rotation, side).

## How to work with the schematic

- **When citing a connection, name the net and the pins** - not just a part name or
  assumption.
- **DESIGN.md can drift out of sync with the BOM.** Treat any part name/number it states as
  a claim to verify, not fact. Missing a value entirely? Ask, don't guess.
- **Designators aren't stable across revisions.** The schematic tool can renumber them
  (e.g. D2/D3/D4) with no functional change. Always confirm what a designator means against
  the netlist/BOM under review - never carry it forward from memory or a prior pass.
- **Verify part specifics against datasheets, not training data** - pin functions,
  strapping/boot behavior, passive values, current figures. State confidence per item.
  Check `components/<PART>.md` first if one exists (a human-reviewed extract of exactly
  this), before opening the raw PDF.
- **Netlist file layout.** The `.net` file is Protel2 format: component-definition blocks
  first, then all net blocks after. `grep -n '^($'` jumps straight to the net section. Each
  net block is a net name line followed by member lines shaped
  `<Designator>-<Pin#> <PartType>-<PinName> <Passive/Input/...>`. `<PinName>` is usually a real
  functional name (`BOOT0`, `VDD`, `G`/`S`/`D`) - trust it, except bare 2-terminal parts
  (diodes, fuses, simple connectors), which may show only a raw pin number and need datasheet
  confirmation. Unlabeled nets show up as auto-generated names like `$1N165`, `$2N76` - these
  carry no meaning, don't read intent into them.
- **Known EasyEDA library pin-label typos are won't-fix.** Some official library symbols
  contain cosmetic pin-name typos: VL53L8CX's `SPI_ISC_N`/`RSDV1`/`REVD2` instead of
  the datasheet's `SPI_I2C_N`/`RSVD1`/`RSVD2`. These are not schematic errors to correct.
- **BOM rows are per distinct part, not per instance.** `Designator` is a comma-separated
  list of all reference designators sharing that row, and `Quantity` already reflects that
  count. For part identity, trust the `Manufacturer Part` column only - `Comment`/`Value` can
  be generic or misleading (e.g. a row's `Comment` can be just a crystal frequency like
  `"13.56MHz"` rather than the actual chip part number). The `Supplier`/`Supplier Part`
  columns already give the exact LCSC part number (e.g. `C25854`) for every row - check
  these before searching the web for a distributor part number.

## How to review

Use the [pcba-design-skills](https://github.com/Keitark/pcba-design-skills) for a full review:
- `/plan-electronic-product` - requirements/architecture before a circuit exists.
- Check that for each component a `components/` and/or `datasheets/` document is available.
- `/design-and-review-circuit` - schematic/circuit review (protection, strapping pins, power,
  connectors, pin accounting).
  Augment the review checklist with the `.claude/references/pcb-checklist/schematic-checklist.md`.
- `/qualify-pcba-sourcing` - BOM part sourcing, exact MPNs, lifecycle.
- `/pcb-layout-review` - placement, routing, and other layout-facing concerns.
  Augment the review checklist with the `.claude/references/pcb-checklist/layout-checklist.md`.

## Conventions

- Never call Edit/Write on `DESIGN.md` or `CLAUDE.md` without first showing the exact proposed
  text and getting explicit confirmation.
- In Markdown use ASCII characters only.
- Units follow SI style with a space: `90 mA`, `3.3 V`, `2 Mbit`, `84 KB`.
- This is open hardware; keep explanations clear enough for an outside contributor who has
  not seen the internal history.
