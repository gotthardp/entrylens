# Instructions

This file guides Claude Code when working on the Entrylens hardware: which files are
authoritative, how to read the EDA exports, how to run reviews, and how to edit the
documentation. What the product is and how it is designed is described in `DESIGN.md`.

## Sources of truth

Different files are authoritative for different things. If two disagree, flag it rather than
assume which one is right.

| Authoritative source | Topic |
|---|---|
| `DESIGN.md` | Design intent: power rails, current budget, operating states, debug/flashing scheme |
| `DESIGN.md` Section 3.1 | Non-PCB parts: enclosure, light pipe, antenna board, cabling |
| `components/` and `datasheets/` | Component characteristics: pin functions, electrical limits |
| Netlist and BOM export | Component list, designators, exact part numbers |
| Native EasyEDA project | Stackup and design rules |
| `.pcba-workflow/` | Review progress and open unknowns |
| `EntrylensHousing.FCStd` | Enclosure geometry and the mechanical fit of the PCB and antenna board |

### DESIGN.md

Written and maintained by hand; read it first. It can drift out of sync with the BOM, so treat any
part name or number it states as a claim to verify, not fact. If a value is missing entirely, ask
rather than guess.

### datasheets/ and components/

`datasheets/` holds raw vendor datasheets and app notes. Read the local file first and fetch from
the web only if no local copy exists. Files are added as work proceeds, so list the directory when
you need it rather than trusting an earlier listing.

`components/<PART>.md` files are human-reviewed per-part extracts (see `components/_template.md`)
naming which datasheets cover each part. They are hand-curated, not regenerated, so re-check them
after a part swap. For parts without one, match the datasheet filename against the BOM's
`Manufacturer Part` column.

### .pcba-workflow/

Running state of the review skills, not hand-written: `product-brief.yaml` (requirements and open
unknowns), `architecture.md`, `circuit-review.md`, `layout-review.json` and `sourcing-lock.csv`.
Read the brief's `unknowns` before re-deriving what is already known to be open.

### EntrylensHousing.FCStd

FreeCAD model of the enclosure, maintained by hand. It also contains imported 3D models of the PCB
assembly and the 2JF0415P antenna board for checking the fit. Take component data from the
netlist and BOM, not from these imports, which may lag the current revision.

### EDA export

Auto-generated by the EDA tool:
- `Netlist_Schematic1_*.net`: Protel2-format netlist
- `BOM_Board1_PCB1_*.csv`: bill of materials
- `Gerber_PCB1_*.zip`: fabrication Gerbers and drill files, plus `FlyingProbeTesting.json`
- `PickAndPlace_PCB1_*.csv`: component placement (position, rotation, side)
- `ProPrj_*.epro2`: native EasyEDA Pro project

Never mix revisions. The same date is not sufficient: a partial re-export leaves files hours apart,
so compare modification times before cross-checking them.

Assume the designer ran DRC before export; no report is generated.

## Reading the files

### Netlist

The `.net` file has component-definition blocks first, then all net blocks; `grep -n '^($'` jumps
straight to the net section. Each net block is a net name line followed by member lines shaped
`<Designator>-<Pin#> <PartType>-<PinName> <Passive/Input/...>`.

`<PinName>` is usually a real functional name (`BOOT0`, `VDD`, `G`/`S`/`D`) - trust it. The
exception is bare 2-terminal parts (diodes, fuses, simple connectors), which may show only a raw
pin number and need datasheet confirmation.

Unlabeled nets show up as auto-generated names like `$1N165` or `$2N76`. These carry no meaning;
don't read intent into them.

### BOM

Rows are per distinct part, not per instance. `Designator` is a comma-separated list of all
reference designators sharing that row, and `Quantity` already reflects that count.

For part identity, trust the `Manufacturer Part` column only. `Comment`/`Value` can be generic or
misleading; for example, a row's `Comment` can be just a crystal frequency like `"13.56MHz"`
rather than the actual chip part number.

The `Supplier`/`Supplier Part` columns give the exact LCSC part number (e.g. `C25854`) for every
row. Check these before searching the web for a distributor part number.

The `JLCPCB Part Class` column states Basic or Extended directly. Read it rather than inferring,
since each distinct Extended part number adds a one-time feeder fee.

The `JLCPCB Price` column is assembly cost, not component cost: what it costs to place the part.
A 32-pin module therefore reads high, and the JLC QR code appears there with no component behind
it. Take component prices from the supplier.

### FlyingProbeTesting.json

A per-pin net list extracted from the layout, usable to cross-check layout connectivity against
the netlist. It renames translated nets to `NET_1`, `NET_2` and so on, so comparing net *names*
against the netlist produces dozens of false mismatches. Compare the net *partitions* - the sets
of pins grouped together - not the names.

It also lists vias and JLC test points under `PAD<n>` and `TPJLC` pseudo-designators. Filter those
out before comparing partitions, or every net appears to mismatch.

### Native EasyEDA Pro project

`ProPrj_*.epro2` is a zip; the board and schematic live in `<name>.epru` as a sequence of
`{header}||{payload}` chunks separated by `|` and a newline. Split the file on `|\n`, then split
each chunk on `||` to get the typed header (`{"type":"LINE",...}`) and its untyped payload.

Coordinates are mils. `LAYER_PHYS` holds the stackup, `POUR` the plane net and layer, `LINE` and
`VIA` the routing, and `COMPONENT` plus `ATTR` the placement. This is the only source for stackup
and design rules; the Gerbers do not carry them.

### FreeCAD model

`EntrylensHousing.FCStd` is a zip. `Document.xml` holds the feature tree, object labels and
properties; each shape is stored as an OpenCASCADE BREP file named `<object>.Shape.brp`. The
imported PCB parts carry EasyEDA labels such as `C10~C0603~...`.

### Known non-issues

- **EasyEDA library pin-label typos are won't-fix.** Some official library symbols contain
  cosmetic pin-name typos: VL53L8CX's `SPI_ISC_N`/`RSDV1`/`REVD2` instead of the datasheet's
  `SPI_I2C_N`/`RSVD1`/`RSVD2`. These are not schematic errors to correct.
- **The NFC antenna is PCB copper, not a schematic part.** ST25DV `AC0` and `AC1` therefore share
  one net (`ANT-C6`) in both the netlist and `FlyingProbeTesting.json`; the coil separates them
  only in the layout. This is not a short. The coil is checkable only geometrically, from the
  Gerbers.

## Working rules

- **When citing a connection, name the net and the pins**, not just a part name or assumption.
- **Designators aren't stable across revisions.** The schematic tool can renumber them (e.g.
  D2/D3/D4) with no functional change. Always confirm what a designator means against the
  netlist/BOM under review; never carry it forward from memory or a prior pass.
- **Verify part specifics against datasheets, not training data**: pin functions, strapping/boot
  behavior, passive values, current figures. State confidence per item. Check
  `components/<PART>.md` first if one exists, before opening the raw PDF.
- **Never violate a datasheet recommendation.** If two datasheets conflict, that is a finding to
  raise, not a trade-off to make quietly - stop and report the conflict.

## Part selection

Prefer established manufacturers: those with their own production, complete and dated
datasheets, and a record of volume supply. Asian mass producers qualify (for example Samsung
Electro-Mechanics, Murata, TDK, Yageo, UNI-ROYAL, Fenghua, Sunlord, PUYA, Lite-On, Everlight).
Small no-name vendors and relabelling brands do not, even when JLC lists them as Basic or
Preferred.

Paying slightly more for a reputable vendor, including an Extended-part fee, is acceptable. Apply
this to alternates and second sources, and flag existing BOM lines that fail it.

## Reviews

Use the [pcba-design-skills](https://github.com/Keitark/pcba-design-skills) for a full review:
- `/plan-electronic-product`: requirements and architecture before a circuit exists.
- Component coverage: check that each component has a `components/` and/or `datasheets/`
  document. Read the `components/<PART>.md` References block first - a datasheet it records as
  online-only is coverage, not a gap; `ls datasheets/` alone is not the check.
- `/design-and-review-circuit`: schematic/circuit review (protection, strapping pins, power,
  connectors, pin accounting).
- `/qualify-pcba-sourcing`: BOM part sourcing, exact MPNs, lifecycle.
- `/pcb-layout-review`: placement, routing and other layout-facing concerns.

### Extra review items

Augment the skills' own checklists from two sources:
- [pcb-checklist](https://github.com/azonenberg/pcb-checklist), cloned into
  `.claude/references/pcb-checklist` (not tracked in this repository)
- The local items below, which cover what neither the skills nor pcb-checklist check

`/design-and-review-circuit` is augmented by
`.claude/references/pcb-checklist/schematic-checklist.md`, plus:
- Every cable longer than about 3 m, including the power cable of up to 20 m, has common-mode
  filtering.
- Every external port withstands the immunity tests that EN 301 489-1 Table 2 applies to it:
  ESD (IEC 61000-4-2) and RF field (IEC 61000-4-3) on the enclosure; burst (IEC 61000-4-4) and RF
  common mode (IEC 61000-4-6) on ports whose cables may exceed 3 m; surge (IEC 61000-4-5) only on
  AC mains and wired network ports.

`/pcb-layout-review` is augmented by `.claude/references/pcb-checklist/layout-checklist.md`, plus:
- Each ground pad has its own via to the reference plane.
- Every layer change of a fast signal has a ground via next to the signal via.
- Traces enter SMD pads from the end, not the side.
- A ground test loop gives an oscilloscope clip somewhere to go.

## Editing documents

Never call Edit/Write on `DESIGN.md` or `CLAUDE.md` without first showing the exact proposed text
and getting explicit confirmation.

This is open hardware. Keep explanations clear enough for an outside contributor who has not seen
the internal history.

Markdown style:
- Characters: ASCII only
- Units: SI style with a space, e.g. `90 mA`, `3.3 V`, `2 Mbit`, `84 KB`

### Writing DESIGN.md

Keep `DESIGN.md` concise but readable. State each decision and its value, with a short reason where
it is not obvious, and use connecting prose rather than turning everything into lists.

- Keep one subject per paragraph and per list.
- Use tables or lists only for data a reader looks up (specs, dimension sets, pinouts, part
  lists); values that belong to a statement or explain a decision can sit in a sentence.
- Write list items that describe things as phrases with a verb or relation word, not
  comma-joined fragments. Terse `label: value` lines suit only pure spec data such as
  temperature, thickness or a pinout.
- Do not write derivation narratives or restate a datasheet's argument; name the part and let
  `components/` carry the detail.
- Do not restate what the schematic or BOM shows directly: exact passive values, pin assignments,
  net connectivity, pull-ups and pull-downs, or which rail supplies a part. Mention such a detail
  only as part of a decision or constraint, together with its reason. Connector pinouts are the
  exception.
